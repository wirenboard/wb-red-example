# wb-red-example

Пример организации резервированной пары контроллеров Wiren Board (active/standby) с общими Modbus-модулями за одним шлюзом WB-MGE. Собран и проверен на паре контроллеров 192.168.143.111 и 192.168.143.112 с WB-MGE 192.168.143.113.

Пример носит учебный и демонстрационный характер и не проходил испытаний в реальных установках. Перед применением на объекте проверьте его работу самостоятельно: ответственность за последствия использования примера несёт тот, кто его применяет. Репозиторий опубликован для ссылки из статьи на вики. Перед копированием файлов на контроллеры замените в них значения из раздела «Что заменить перед копированием файлов».

## Архитектура

- Оба контроллера независимо опрашивают одни и те же Modbus-устройства через общий WB-MGE: порт шлюза работает в режиме «Modbus TCP», в котором к одному порту можно одновременно подключить до 8 TCP-клиентов.
- Роль узла (active/standby) определяет `keepalived` по протоколу VRRP.
- Health-check для VRRP проверяет работу автоматики (службы `wb-rules` и `wb-mqtt-serial`) и доступность WB-MGE.
- Читать данные с устройств могут оба узла. Запись в устройства выполняется только с активного узла через общий модуль wb-rules `wbha.js`.
- Роль, виртуальный IP и приоритет публикуются в MQTT и отображаются в виртуальном устройстве «Статус резервирования» в веб-интерфейсе каждого контроллера.

### Если узлы подключены по Wi-Fi

При подключении узлов по Wi-Fi в `keepalived.conf` нужны две дополнительные настройки:

- **`unicast_src_ip`/`unicast_peer`** вместо мультикаста по умолчанию: точки доступа Wi-Fi часто блокируют мультикаст-трафик между клиентами.
- **`dont_track_primary`**: без неё при кратковременном пропадании интерфейса (переподключение к Wi-Fi) `keepalived` переходит в состояние `FAULT` и сам из него не выходит.

При проводном подключении эти настройки обычно не нужны.

Конфиги и скрипты в репозитории подготовлены для подключения по Wi-Fi: в них есть эти настройки и указан интерфейс `wlan0`. При проводном подключении замените `wlan0` на имя проводного интерфейса.

## Структура репозитория

```
keepalived/
  keepalived.conf.111     — конфиг VRRP для узла с priority 150 (master по умолчанию)
  keepalived.conf.112     — конфиг VRRP для узла с priority 100 (backup по умолчанию)
  override.conf           — systemd drop-in: ждать стабильный IP перед стартом keepalived
  replica.snippet.conf    — блок vrrp_script для проверки реплики (только для репликации состояния)
scripts/                  — /usr/local/bin/ на обоих узлах
  wb-ha-healthcheck.sh    — health-check для vrrp_script (автоматика + доступность WB-MGE)
  wb-ha-notify.sh         — публикует роль, VIP и приоритет при смене состояния VRRP
  wb-ha-role-heartbeat.sh — повторно публикует роль раз в минуту (cron)
  wb-ha-wait-for-ip.sh    — ждёт стабильного появления IP перед стартом keepalived
  wb-ha-replica-gate.sh   — проверка реплики для vrrp_script (только для репликации состояния)
cron/
  wb-ha-role-heartbeat    — запуск wb-ha-role-heartbeat.sh раз в минуту
mosquitto/
  000persistence.conf          — сохранение retained-сообщений при перезапуске брокера
  wb-ha-bridge.conf.111, .112  — мост репликации для первого и второго узла (только для репликации состояния)
wb-rules/
  wbha.js                   — модуль проверки роли при записи (на обоих узлах, без правок)
  wb_ha_status.js           — виртуальное устройство для отображения роли (на обоих узлах, без правок)
  wbreplica.js              — запоминает реплику соседа и применяет её при переходе в active (только для репликации состояния)
  wb_ha_test_setpoint.js    — тестовая уставка для проверки репликации (только для репликации состояния)
  motion_light.js           — пример правила, использующего wbha.dev()
```

`wb-ha-notify.sh` и `wb-ha-role-heartbeat.sh` содержат константу `PRIORITY` (150 на узле с бо́льшим приоритетом, 100 на другом): она должна совпадать со значением `priority` в `keepalived.conf` этого же узла. `wb-ha-wait-for-ip.sh` содержит IP своего узла. `wbha.js` и `wb_ha_status.js` одинаковы на обоих узлах.

## Порядок установки (кратко)

1. На каждом контроллере добавить в настройках драйвера wb-mqtt-serial порт типа Modbus TCP: указать IP-адрес WB-MGE и TCP-порт шлюза (по умолчанию 502 — RS-485-1, 503 — RS-485-2), затем добавить на порт устройства.
2. `apt-get install -y keepalived` на оба узла.
3. Разложить `keepalived.conf.*` → `/etc/keepalived/keepalived.conf` (свой файл на каждый узел). Создать каталог командой `mkdir -p /etc/systemd/system/keepalived.service.d`, положить в него `override.conf` → `/etc/systemd/system/keepalived.service.d/override.conf`, затем выполнить `systemctl daemon-reload`.
4. Скрипты из `scripts/` → `/usr/local/bin/`, затем `chown root:root /usr/local/bin/wb-ha-*.sh` и `chmod 755 /usr/local/bin/wb-ha-*.sh`.
5. Скопировать на оба узла `cron/wb-ha-role-heartbeat` → `/etc/cron.d/wb-ha-role-heartbeat`, затем `chown root:root /etc/cron.d/wb-ha-role-heartbeat` и `chmod 644 /etc/cron.d/wb-ha-role-heartbeat`.
6. `mosquitto/000persistence.conf` → `/etc/mosquitto/conf.d/`.
7. Скопировать на оба узла (файлы одинаковые на обоих узлах):
   - `wb-rules/wbha.js` → `/etc/wb-rules-modules/wbha.js`;
   - `wb-rules/wb_ha_status.js` → `/etc/wb-rules/wb_ha_status.js`;
   - `wb-rules/motion_light.js` → `/etc/wb-rules/motion_light.js`.

   **Примечание.** Файл `motion_light.js` содержит пути к реальному оборудованию: `wb-mr6c_112/K1` и `wb-msw-v4_155/Current Motion`. Перед копированием скорректируйте их в соответствии с вашей установкой.
8. Перезапустить `keepalived`, `mosquitto`, `wb-rules` на обоих узлах.
9. Проверить работу пары тестами на контроллерах, см. «Тайминги, подтверждённые тестами».

## Тайминги, подтверждённые тестами

- Отключение питания или сети на активном узле: резервный узел становится активным примерно через 3 с (срабатывание протокола VRRP).
- Отказ автоматики при работающей ОС (`systemctl stop wb-rules`): резервный узел становится активным примерно через 8 с. Оба узла одновременно в роли active при этом не оказываются: по логам `keepalived` обоих узлов переход синхронный, расхождение менее 10 мс.
- Восстановление автоматики: роль возвращается исходному узлу примерно через 2,4 с.
- Две перезагрузки обоих узлов подряд: состояние `FAULT` не возникало.
- Пропадание связи с WB-MGE при работающих службах: health-check (`wb-ha-healthcheck.sh`) снимает узлу приоритет, и роль переходит к соседу.

## Два активных узла при разрыве связи между ними

Если пропадает связь между узлами пары, но у обоих сохраняется связь с остальной сетью и с WB-MGE, **оба узла становятся `active` и оба удерживают VIP**. Это подтверждено тестом: связь между узлами блокировалась через `iptables`. Пара из двух узлов VRRP без третьего узла-арбитра не может этого предотвратить: `dont_track_primary`, `preempt_delay` и проверка доступности WB-MGE здесь не помогают, так как каждый узел считает соседа отказавшим.

После снятия блокировки роли автоматически распределяются штатно, без `FAULT`.

Возможные решения (не реализованы):

- проверка роли при записи в `wbha.js` по дополнительному независимому каналу связи между узлами. Через приоритет VRRP (`vrrp_script`/`weight`) это сделать нельзя: `keepalived` переводит резервный узел в master по таймауту независимо от приоритета;
- остановка `keepalived` на резервном узле, если по независимому каналу видно, что активный узел работает.

При проводном подключении узлов звездой через коммутатор вероятность разрыва связи только между узлами пары ниже, чем при Wi-Fi, но проблема не устраняется.

## Репликация состояния между узлами (необязательно)

Репликация переносит на соседний узел значения, которых нет в устройствах: уставки, ручные режимы, значения виртуальных устройств. Без неё такое значение существует только на том узле, где его задали, и при отказе активного узла резервный о нём не знает. Базовое резервирование выше работает и без репликации.

Как это работает:

- На каждом узле есть односторонний мост mosquitto (`out`) к брокеру соседа. Он отправляет значения этого узла соседу в `/replica/remote/...`: на каждом узле в `/replica` лежат только копии значений соседа.
- Что реплицируется, определяют строки `topic` в файле моста. Другого списка нет: для нового значения добавьте такую строку на обоих узлах.
- `wbreplica.js` запоминает значения из `/replica` и применяет их, только когда узел переходит из `standby` или `fault` в `active`. Значения только для чтения и кнопки пропускаются.
- Проверка реплики (`wb-ha-replica-gate.sh`, вызывается из `keepalived` блоком `chk_replica_fresh`) не даёт узлу, не держащему виртуальный IP, стать `active`, пока к нему не подключён мост соседа. Иначе вернувшийся после перезагрузки узел с высоким приоритетом применил бы устаревшую реплику и затёр новые значения. Подключение определяется по установленному соединению соседа на порту 1883 (`ss`), поэтому проверка не зависит от wb-rules соседа.

### Что заменить перед копированием файлов (репликация)

| Файл | Строка | Параметр | Что указать | На узлах |
|---|---|---|---|---|
| `mosquitto/wb-ha-bridge.conf.111`, `mosquitto/wb-ha-bridge.conf.112` | 7 | `address` | в файле `.111` — IP-адрес второго узла, в файле `.112` — IP-адрес первого узла | **разное** |
| `mosquitto/wb-ha-bridge.conf.111`, `mosquitto/wb-ha-bridge.conf.112` | 11 | `topic` | если реплицируется не тестовая уставка из примера, замените `wb_ha_test` на своё устройство; для других значений добавьте строки | одинаково |
| `scripts/wb-ha-replica-gate.sh` | 12 | `IFACE` | имя сетевого интерфейса, как в `interface` в `keepalived.conf` | одинаково |
| `scripts/wb-ha-replica-gate.sh` | 13 | `VIP` | виртуальный IP-адрес без маски | одинаково |

### Порядок установки репликации (кратко)

Репликацию настраивают на уже работающей паре.

1. Скопировать мост: `mosquitto/wb-ha-bridge.conf.111` → `/etc/mosquitto/conf.d/wb-ha-bridge.conf` на первом узле, `mosquitto/wb-ha-bridge.conf.112` → туда же на втором.
2. На оба узла: `scripts/wb-ha-replica-gate.sh` → `/usr/local/bin/` (затем `chown root:root` и `chmod 755`), `wb-rules/wbreplica.js` и `wb-rules/wb_ha_test_setpoint.js` → `/etc/wb-rules/`.
3. В `/etc/keepalived/keepalived.conf` обоих узлов вставить блок `vrrp_script chk_replica_fresh` из `keepalived/replica.snippet.conf` перед `vrrp_instance` и добавить строку `chk_replica_fresh` в `track_script`. Проверить файл: `keepalived --config-test -f /etc/keepalived/keepalived.conf`.
4. Перезапустить `mosquitto` и `wb-rules` (сначала на резервном узле, затем на активном).
5. Перечитать настройки `keepalived` командой `systemctl reload keepalived` (не `restart`), сначала на резервном узле, затем на активном: при перезагрузке настроек роли не переключаются.
6. Запустить `wb-ha-replica-gate.sh` на каждом узле: на узле с виртуальным IP код всегда 0, на резервном — 0 при подключённом мосте соседа.

Не включайте `in` в мосте на обоих узлах одновременно: каждое значение пойдёт по двум соединениям.

### Что проверено (репликация)

- Репликация в обе стороны без дублей: одно изменение приходит одним сообщением.
- Отказ автоматики на активном узле (`systemctl stop wb-rules`): резервный узел становится активным за 14–18 с и применяет реплику; вернувшийся узел применяет новое значение.
- Перезагрузка узла с высоким приоритетом при недоступном канале репликации: узел остаётся `standby`, пока мост соседа не подключится, затем становится `active` и применяет свежее значение.

### Ограничения репликации

- Реплика применяется только при переходе в `active` из `standby` или `fault`. Если узел сразу запустился в роли `active`, реплика не применяется.
- Проверка реплики видит подключение моста, но не свежесть данных. При тихом обрыве Wi-Fi соединение может считаться живым до 60 с.
- Если у активного узла перестаёт отвечать WB-MGE (приоритет падает на 60), а у вернувшегося узла с высоким приоритетом мост соседа ещё не подключён (тоже −60), вернувшийся узел становится активным и применяет устаревшую реплику. В тестах такое наблюдалось один раз. Если сделать вес `chk_replica_fresh` по модулю больше веса `chk_wb_automation`, этот случай исключается, но при неисправной автоматике активного узла роль останется на нём.
- Между появлением виртуального IP и применением реплики проходят десятки миллисекунд.
- При разрыве связи между узлами оба узла становятся `active`, и реплики расходятся (см. раздел про два активных узла выше).

## Не реализовано

- Резервирование WB-MGE: это единая точка отказа для чтения и управления с обоих контроллеров.
- Синхронизация состояния автоматики (таймеров и счётчиков `wb-rules`) между узлами: каждый узел ведёт его самостоятельно, начиная с момента своего запуска.
